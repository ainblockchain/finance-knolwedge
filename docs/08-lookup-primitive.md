# "지식 조회 원시연산"은 어떻게 만들어졌나 — 구성요소별 해부

목적: Engram 팀이 "트랜스포머에 없는 O(1) 지식 조회"를 **무엇으로, 왜 그렇게**
만들었는지, 그리고 Qwen3.8 이 그것을 **실제로 어떻게 구현**했는지를 부품
단위로 밝힌다.  근거는 논문 §2 수식, 공식 데모 코드, 그리고 우리가 서빙 중인
vLLM 의 Qwen 구현 (`docs/papers/qwen-vllm-src/ple_layer.py`, 1,244줄) 과
체크포인트 `config.json` 이다.

---

## 0. 원시연산의 정의

입력 토큰 열만 보고, 계산 없이, 고정된 주소에서 벡터를 꺼내 잔차에 더한다.

```
lookup(x_{t-2}, x_{t-1}, x_t)  →  e_t ∈ R^2560       (O(1), 입력만으로 결정)
h_t  ←  h_t + fuse(e_t, h_t)                          (문맥이 동의하는 만큼)
```

MoE 의 라우팅은 hidden state 를 봐야 결정되지만 이것은 **토큰 id 만으로**
결정된다.  이 한 가지 성질에서 선인출·오프로드·편집 가능성이 모두 나온다.

## 1. 부품 1 — 키 만들기: 토큰 열 → 정수

### 1.1 창 (window)

직전 토큰 `ngram_size = 3` 개만 본다 (`config.json`).  차수 2 와 3 을 따로
쓴다 (1-gram 은 입력 임베딩이 이미 하므로 제외).  논문 §6.2: 4-gram 은 고정
예산에서 손해 — 2/3-gram 이 훨씬 빈번하고 용량을 나눠 갖기 때문.

### 1.2 문서 경계 [Qwen 구현 고유]

```python
# _shift_precompute / _shift_apply
position_in_segment = 위치 − 직전 EOS 위치 − 1
shift 가 segment 를 넘으면 그 자리는 EOS id 로 대체
```

n-gram 은 **EOS 를 넘어 이어지지 않는다.**  한 요청의 첫 토큰은 `(EOS, EOS, x_0)`
으로 해시된다.  데모 코드는 `pad_id` 로 왼쪽을 채우는 것만 있었고, Qwen 은
문서 경계 재설정을 추가했다.  또 `ngram_context` 버퍼로 요청의 **직전 2 토큰**을
디코드 스텝마다 넘겨서, 한 토큰씩 생성할 때도 창이 유지된다.

### 1.3 토크나이저 압축 — Engram 은 채택, Qwen 은 미채택

Engram 데모: NFKC → NFD → 악센트 제거 → 소문자 → 공백 정규화로 `Apple`/`␣apple`
을 같은 id 로 접는다 (128k → 23% 감소).  §6.2 에서 핵심 3요소.
Qwen 보고서 §2.3.2: "일관된 이득 없음" 으로 **미채택**.  Qwen 코드에도 압축
단계가 없고 원 토큰 id 가 바로 해시에 들어간다.  우리 주소 검증이 원 id 로
맞은 것과 일치한다.

### 1.4 해시 — 승수-XOR

```python
mix = x_t·m_0  ^  x_{t-1}·m_1  ^  x_{t-2}·m_2        (3-gram; 2-gram 은 앞 둘만)
```

- 승수 `m_j` 는 **홀수**이며 `2·(splitmix64(seed + 10007·layer + γ·(j+1)) mod half) + 1`.
  홀수인 이유: 짝수 승수는 하위 비트를 버린다.  데모는 `rng.integers·2+1`,
  Qwen 은 splitmix64 로 바꿨다 — 재현성 있는 결정론적 상수.
- XOR 인 이유: 덧셈보다 비트 섞임이 좋고, 위치별 승수가 다르므로 `A B` ≠ `B A`.
- 64비트 안에서 오버플로 없이 계산되도록 `m < 2^63 / vocab`.

### 1.5 다중 헤드와 소수 모듈로

```python
addr_k = offset_k + (mix mod p_k),   p_k = 20,000,000 − 1 뒤의 k+1 번째 소수
```

- 헤드 `heads_per_ngram = 8`: **같은 `mix` 를 서로 다른 소수로 나눈다.**
  한 헤드에서 충돌한 두 n-gram 이 다른 헤드에서도 충돌할 확률은 거의 0 →
  8 개 중 7 개는 깨끗하다.  (Svenstrup 2017 의 hash embedding 계보.)
- 소수인 이유: 모듈로가 합성수면 `mix` 의 하위 비트 구조와 상호작용해
  분포가 치우친다.  연속 소수 20,000,003 … 20,000,171 (`_nth_prime_after`).
- 16 헤드를 `offset_k` 로 **한 테이블에 이어붙인다** → 320,001,536 행 (128 배수로
  패딩).  헤드 하나의 행은 160 차원 (`ple_embed_dim 2560 / 16`).

Tensorizing Engram (2606.08347) 이 문제 삼는 것이 바로 이 "차수·헤드별 독립
테이블의 충돌" 이다.

## 2. 부품 2 — 값 꺼내기: 정수 → 벡터

```python
e_t = index_select(E, [addr_0 … addr_15]).reshape(2560)
```

그게 전부다.  곱셈이 없다.  `E` 는 `[320,001,536, 160]` bf16 (FP8 옵션 있음).
GPU 경로에선 `VocabParallelEmbedding`, CPU 오프로드 경로에선 `index_select` 로
핀 메모리 버퍼에 직접 쓴다 (`forward_impl`, `output_buffer`).

## 3. 부품 3 — 융합: 벡터를 잔차에 넣되, 문맥이 허락할 때만

### 3.1 문제

꺼낸 `e_t` 는 **문맥 독립적 사전값**이다.  충돌한 다른 n-gram, 다의어, 한 행에
섞인 여러 문맥이 다 들어 있다.  그대로 더하면 잡음이다.

### 3.2 해법: 어텐션 모양의 스칼라 게이트 (논문 §2.3, Qwen `forward`)

```python
key_b   = RMSNorm_grouped( W_K e_t )[b]        W_K: 2560 → 4·2560  (가지 4개 각각)
value   = W_V e_t                              W_V: 2560 → 2560    (가지 공유)
query_b = RMSNorm_grouped( h_t[b] )            h_t: 가지 4개의 잔차
s_b     = ⟨key_b, query_b⟩ / √2560
g_b     = σ( sign(s_b) · √max(|s_b|, 1e-6) )
out_b   = g_b · value
```

- `h_t` 가 Query: 앞 층(어텐션 1회)이 모은 문맥.  §6.2: layer 1 은 문맥이
  부족해 게이트가 부정확, 깊으면 정적 재구성을 이미 백본이 해버림 → **layer 2**
  (0-index 1) 가 최적.  Qwen config `ple_layer_ids [2]` (1-index) = 텐서 `layers.1.ple`.
- 행이 **자기 키를 갖는다**: `W_K e_t` — "나는 이런 문맥에서 쓰여야 한다".
  같은 행을 쓰는 다른 n-gram 의 문맥에선 내적이 작아 닫힌다.  충돌 방어의
  두 번째 층이다 (첫 번째는 다중 헤드).
- RMSNorm 을 양쪽에: 내적 크기가 폭주하지 않게 (Dehghani 2023).
- `sign·√|s|`: 시그모이드 앞에서 압축.  내적이 커도 게이트가 급포화하지 않고,
  0 근처 기울기를 유지한다.
- **가지별 게이트, 값 공유** (§2.4): Qwen 의 Gated Residual 은 잔차를 4 가지로
  넓힌다.  각 가지가 자기 `W_K^b` 로 따로 판단하고 같은 `value` 를 받는다.
  `W_K`(2560→10240) 와 `W_V`(2560→2560) 를 하나의 행렬곱으로 융합해 FP8 로
  돌린다.  §6.2 에서 "가지별 융합 제거" 가 가장 큰 손실.

### 3.3 conv: 창을 3 너머로 조금 넓힌다 (논문 식 5, Qwen `_short_conv`)

```python
u_t = RMSNorm_grouped(out_t)
c_t = SiLU( Σ_{i=0..3} w_i · u_{t − 3i} )     depthwise, kernel 4, dilation 3
PLE_out_t = out_t + c_t
```

- dilation = `ngram_size` = 3: 커널이 t, t−3, t−6, t−9 를 본다.  즉 **서로 겹치지
  않는 3-gram 창 4 개**를 잇는다 → 유효 창 12 토큰.
- 가중치 **0 초기화** (`nn.init.zeros_`, `_no_reinit`): 학습 시작 시 identity.
- 논문 §6.2: 제거해도 손실 미미.  Qwen 은 유지.  vLLM 은 이를 Mamba 식
  conv-state 캐시로 구현해 디코드마다 직전 9 토큰의 `u` 를 기억한다
  (`PleShortConvAttentionBackend`).

### 3.4 잔차 결합

`PLE_out_t` (4 가지 × 2560) 이 Gated Residual 의 쓰기 경로로 잔차 4 가지에
더해진다.  그 뒤 GDN/어텐션 + MoE 46 층이 이어진다.

## 4. 부품 4 — 학습이 이 부품들을 어떻게 채우나

(자세히는 `docs/05`, `docs/06`.)  요점만:

- 손실은 다음 토큰 예측 하나.  행 `E[a]` 는 주소 `a` 가 계산된 **모든** 위치의
  기울기 합을 받는다 → "이 열 뒤에 코퍼스에서 뭐가 왔나" 의 가중 평균.
- `W_K`, `W_V`, conv 는 Muon (선형 사상), `E` 는 Adam·학습률 5×·decay 0
  (희소 행 보정, 잊지 않게).
- 게이트가 학습되면서 행의 키 `W_K e` 가 "쓰일 문맥" 쪽으로 정렬된다 —
  충돌 방어가 학습으로 강화된다.

## 5. 부품 5 — 시스템: 왜 이 설계가 오프로드·선인출을 허용하나

- 주소가 토큰 id 만의 함수 → forward **전에** 다음 배치의 주소를 안다.
- 그래서 테이블을 호스트 DRAM 에 두고 (`VLLM_PLE_CPU_OFFLOAD=1`), 별도
  프로세스(`PleOffloadRunner`)가 `index_select` 로 행을 모아 핀 메모리 → GPU
  로 DMA 하고 세마포어로 알린다.  layer 0 계산이 그 시간을 가린다.
- Zipf 분포 → 자주 쓰는 행은 HBM/DRAM, 꼬리는 SSD 로 계층화 가능 (§2.5).
- 편집 훅도 이 성질 위에 있다: 어떤 문맥이 어느 행을 지나는지 정확히 알고,
  CPU 의 행을 바꾸면 다음 forward 부터 반영된다.

## 6. Engram 논문/데모 vs Qwen3.8 구현 — 차이표

| 항목 | Engram (논문/데모) | Qwen3.8 (vLLM 구현 + config) |
|---|---|---|
| 토크나이저 압축 | 있음 (NFKC·소문자 등, 핵심 3요소) | **없음** — 원 id |
| 문서 경계 | pad 로 왼쪽만 채움 | **EOS 에서 창 재설정** + 디코드용 `ngram_context` |
| 승수 생성 | `rng.integers·2+1` | `splitmix64` 기반 홀수 |
| 소수 | 헤드별 다음 소수 | 동일, `_nth_prime_after`, 연속 소수 |
| 테이블 배치 | 헤드별 `nn.Embedding` 이어붙임 | 한 테이블 + `offset`, 128 패딩 |
| 차수 / 헤드 | 2,3 / 8 | 2,3 / 8 (`ngram_size 3, heads_per_ngram 8`) |
| 행 크기 | 헤드당 `n_embed/heads` | 160 (`2560/16`) |
| 층 | 2 와 15 | **한 층** (`ple_layer_ids`) |
| 게이트 | 식 (4), 가지별 | 동일 수식, `hc_count=4`, grouped RMSNorm |
| conv | kernel 4, dilation 3, 0 초기화, SiLU | 동일 + conv-state 캐시 구현 |
| 정밀도 | — | bf16 (FP8 옵션) |
| 옵티마이저 | E: Adam ×5 decay 0 / 나머지 Muon | E: Adam decay 0 / K,V: Muon |

## 7. 이 해부가 편집에 말해주는 것

1. **행 = 주소당 하나의 방향**.  주소는 토큰 열만의 함수이므로 목표 열의
   위치마다 정확히 16 행을 지목할 수 있다 (부품 1).
2. **행은 게이트를 통과해야 한다** (부품 3).  행을 아무리 키워도 `W_K e` 가
   `h_t` 와 안 맞으면 닫힌다.  편집이 통하려면 값 방향(`W_V e`)만이 아니라
   키 방향(`W_K e`)도 현재 문맥에 맞아야 한다.  "안 움직이는 자리" 의 유력한
   원인이다.  UNEMBED_P 초기화가 값 경로만 겨냥하는 것이 약점일 수 있다.
3. **conv 때문에 행 t 는 t+3, t+6, t+9 의 출력에도 조금 닿는다** (부품 3.3).
   여섯 자리 코드 안에서 자리 k 의 편집이 k+3 에 미약하게 새어 들어간다.
   그러나 뒤 방향뿐이다 — 앞 자리를 깨뜨리는 경로는 여전히 없다.
4. **다중 헤드가 부수 피해의 완충**이다.  16 행 중 일부만 고치면 충돌
   상대는 나머지 헤드로 버틴다 (실측 431 → 1 종목).
5. **문서 경계** 때문에 프롬프트 첫 토큰의 주소는 `(EOS, EOS, x_0)` 이다.
   템플릿을 바꾸면 진입 행이 바뀌는 이유가 하나 더 있다.
