## 1. 왜 만들었나 — 설계 의도 [저자]

### 1.1 문제 정의: "트랜스포머에는 조회 원시연산이 없다"

> "Transformers lack a native primitive for knowledge lookup, forcing them to
> inefficiently simulate retrieval through computation." — Engram 초록

O(1) 로 끝나야 할 정적 패턴 완성("Alexander the → Great")을 어텐션·FFN 이
매번 계산으로 재구성하고 있다는 것이 출발점이다.  MoE 가 **조건부 계산**
(입력에 따라 어느 전문가를 돌릴지)이라면, 이것은 **조건부 기억**(입력에 따라
어느 행을 읽을지)이다.  저자들은 이를 "MoE 와 보완적인 **새로운 희소성 축**"
으로 규정한다.

### 1.2 무엇을 담으라고 설계했나: 정적·국소 패턴

- 게이트 시각화 [논문 §6.5]: 게이트가 강하게 열리는 곳은 **다중 토큰 고유명사**
  ("Alexander the Great", "the Milky Way"), **관용구**("By the way", "Princess of
  Wales"), 중국어 **성어·역사 인물**("四大发明", "张仲景").
  "Engram 은 정형화된 언어 의존성을 식별해 처리하며, 백본이 이런 정적 연관을
  외우는 부담을 덜어준다."
- 저장 형태는 **suffix n-gram → 벡터** 로 못 박았다.  "특정 토큰에서 게이트가
  높다는 것은 그 토큰으로 끝나는 선행 토큰들이 정적 패턴으로 인식돼 기억에서
  회수됐다는 뜻" [Figure 7 설명].
- 의도된 효과는 **지식 저장 그 자체보다 백본 해방**이다.  초록·결론이 강조하는
  것은 "초기 층을 정적 재구성에서 풀어줘 실질 깊이를 늘리고, 어텐션이 전역
  문맥에 집중하게 한다"는 것이고, 그래서 지식 벤치마크보다 **추론·코드·수학
  ·장문맥에서 더 큰 이득**이 났다고 쓴다.  지식 벤치마크 붕괴(TriviaQA 29%)
  는 이 설계의 **결과**로 §6.3 에서 확인한 것이지 설계 목표가 아니다.

### 1.3 왜 해시 n-gram 인가: 주소가 입력만으로 결정되기 때문

> "Unlike MoE, which relies on runtime hidden states for dynamic routing,
> Engram's retrieval indices depend solely on the input token sequence." [§2.5]

이 **결정론적 주소**가 설계의 중심축이다.  저자들이 여기서 끌어낸 것:
- 학습: 테이블을 GPU 에 샤딩하고 All-to-All 로 활성 행만 모음 → 용량이 GPU
  수에 선형
- 추론: 다음 forward 의 주소를 **미리** 알므로 호스트 메모리에서 PCIe 로
  선인출(prefetch)하고 앞 층 계산에 숨김.  "100B 테이블을 호스트에 두어도
  오버헤드 무시 가능"
- 배치 층: 모델링은 얕을수록 좋고(§6.2, Layer 2 최적), 시스템은 깊을수록
  선인출 창이 넓다 → "하드웨어-알고리즘 공동 설계" 로 절충
- **다단 캐시 계층** [§2.5]: n-gram 은 Zipf 분포라 "자주 쓰는 행은 HBM/DRAM,
  긴 꼬리는 NVMe SSD" 에 두면 용량을 거의 무한히 키울 수 있다

"기반시설 인식 효율을 **일급 설계 원칙**으로 삼는다" 는 것이 저자들의 표현이다.
테이블을 CPU 에 두고 서빙하는 것은 우회책이 아니라 설계 그 자체다.

### 1.4 어디까지 키우려 했나: "무한 기억 체제"

- §3.1: 고정 예산에서 MoE 와 Engram 의 비율은 **U자** — 순수 MoE 보다 혼합이
  항상 낫다
- §3.2: 백본을 고정하고 슬롯 수만 늘리면 손실이 **log-선형(멱법칙)** 으로 계속
  내려간다.  "추가 계산 없이 더 큰 기억은 계속 이득" — 저자들은 이를
  "예측 가능한 스케일링 손잡이" 라 부른다.
- 결론: "조건부 기억이 차세대 희소 모델의 **필수 모델링 원시연산**이 되리라
  본다" — 이것이 저자들이 직접 쓴 유일한 미래 전망 문장이다.

### 1.5 Qwen 팀의 채택 이유와 판단 [저자: Qwen 보고서]

- README: "N-gram Embedding 은 국소 문맥으로 테이블을 조회해 **아주 적은 추가
  계산으로 용량을 키우며**, 테이블을 호스트 메모리에 내리고 비동기 선인출로
  계산과 겹칠 수 있다."  모델 카드: "MoE 보다 계산이 적고 **오프로드에
  훨씬 유리한** 파라미터 스케일링 축."
- 판단 근거는 Table 7/8/9 의 ablation 이다: 한 층이면 충분, 층 2 가 최적,
  MoE 를 줄여 예산을 옮기면 이득 없음(둘은 **다른 역할**), MoE 고정하고
  테이블만 키우면 손실은 계속 내려가나 벤치마크는 포화 — 단 **중국어처럼
  고유명사·정형 표현이 많은 언어는 계속 오른다**.
- 51B 라는 크기는 "손실 최적"이 아니라 "벤치마크가 포화하는 지점 + 오프로드
  가능한 크기" 의 절충이다 (200V 까지 손실은 내려갔지만 100V~200V 에서
  MMLU 는 64.7→64.9 로 멈춤).

## 2. 저자들이 시도했다가 버린 것 — "이렇게는 바꾸지 마라" [저자]

| 시도 | 결과 | 출처 |
|---|---|---|
| 토크나이저 압축 (대소문자·공백 변형을 같은 id 로) | Engram 에서는 핵심 3요소 중 하나; **Qwen 에서는 일관된 이득 없어 미채택** | Engram §6.2, Qwen §2.3.2 |
| n-gram 차수별 비균등 할당 | 이득 없음 | Qwen §2.3.2 |
| 빈도 기반 슬롯 분할 | 이득 없음 | Qwen §2.3.2 |
| 4-gram 추가 | 고정 예산에선 손해 (2/3-gram 이 더 빈번); 대규모에선 가능성 열어둠 | Engram §6.2 |
| 여러 층에 분산 | Engram 은 2+15 채택; Qwen 은 이득 없어 **한 층** | Engram §6.2, Qwen Table 7 |
| MoE 예산을 줄여 테이블로 이전 | 손실은 10× 에서 최적이나 벤치마크 이득 없음 | Qwen Table 8 |
| ShortConv 제거 | 손실 미미 | Engram §6.2 |
| 게이팅 제거 / 가지별 융합 제거 | 큰 손실 — **제거 불가** | Engram §6.2 |

읽는 법: **주소 체계·게이트·가지별 융합은 건드리지 말고, 크기와 층은 예산에
맞춰 조절하라**는 것이 두 팀의 공통 결론이다.

## 3. 학습 뒤에 바꾸는 것에 대해 저자들이 말한 것

### 3.1 직접 언급: 없다 [저자]

Engram 논문, DeepSeek 공식 저장소 README/issue, Qwen 보고서, Qwen 모델 카드
어디에도 **학습 뒤 테이블을 갱신·편집·교체하는 것**에 대한 문장이 없다.
사후 학습(SFT/RL)에서 테이블을 동결했는지 갱신했는지도 밝히지 않는다.
Engram 저장소 issue #22("memory/persistence 요청")는 사용자 대화 기억 요청
모음이고 관리자 답변이 없다.

### 3.2 설계가 암묵적으로 허용하는 것 [저자 문장에서의 추론]

그러나 저자들이 못 박은 성질들은 사후 편집에 유리한 쪽으로 정렬돼 있다:

1. **주소가 입력만으로 결정** → 어떤 사실이 어느 행을 지나는지 서빙 중에도
   정확히 안다.  MoE 라우팅은 hidden state 에 의존해 이게 불가능하다.
2. **weight decay 0, Adam** → 행은 자연 감쇠하지 않도록 학습됐다.  써 넣은
   값이 저절로 사라질 구조가 아니다.
3. **테이블이 CPU 에 있고 layer 2 한 곳** → 재기동 없이 행을 바꿔 넣을 수
   있고, 바뀐 행은 그 n-gram 이 나타나는 위치에서만 작동한다.  [실측] 우리
   훅은 47ms 왕복으로 이를 한다.
4. **게이트가 문맥으로 거른다** → 편집한 행이 무관한 문맥에서 열리는 것을
   설계가 막는다.  [실측] 헤드 선택으로 영향 종목 431→1.
5. 관련 연구 절에서 저자들이 **ROME/MEMIT(재학습 없는 사실 갱신)** 을 명시적으로
   언급하며 "FFN 이 key-value 기억" 이라는 계보에 자기 모듈을 놓는다 [§7].
   즉 "지식 저장소 → 편집 가능" 이라는 문맥을 저자들도 알고 있다.

이것은 "저자들이 편집을 의도했다"는 증거는 아니다.  "**편집을 막지 않는
방향으로 설계됐다**"까지가 정확한 말이다.

### 3.3 제3자 해설이 말하는 "다음 단계" [해설 — 저자 발언 아님]

중국어 해설(知乎)들은 공통으로 "현재 Engram 은 사전학습에서 **굳어지며**,
중요한 미래 방향은 이 기억 모듈에 **온라인 학습 / 동적 갱신** 능력을 주어
새 지식을 실시간으로 얻게 하는 것" 이라 쓴다.  원문 접근이 막혀(403) 저자
인용인지 해설자 의견인지 확인하지 못했다.  Engram 논문 본문에는 그런 문장이
없으므로 **해설자 의견으로 취급**한다.

## 4. 후속 연구가 바꾸려는 것 [후속]

| 논문 | 무엇을 문제 삼나 | 어떻게 바꾸나 |
|---|---|---|
| **X-GRAM** (2604.21724, Chen 외) | 고정 해시의 세 결함: Zipf 긴 꼬리의 **과소 학습**, 층별 수요 불균형, 슬롯 붕괴(중복 행) | 빈도 인식 동적 토큰 주입, 하이브리드 해시, 꼬리 압축(alias mixing), 깊이 인식 게이트.  테이블 절반으로 +4.4pt |
| **Tensorizing Engram** (2606.08347, Zhou 외) | 차수별 별도 해시 테이블 → **충돌**, 차수 간 잠재 구조 공유 불가 | CP 분해로 토큰-위치 인자 공유.  더 적은 파라미터로 동등 이상 |
| **Scaling Embeddings > Experts** (2601.21204, Liu 외, LongCat) | MoE 의 체감 수익·시스템 병목 | 68.5B 중 **30B+ 를 임베딩**에 배정.  폭·깊이와의 상호작용이 관건 |
| **L³ Large Lookup Layers** (2601.21461, Tseng & De Sa) | MoE 의 동적 라우팅 = 하드웨어 비효율·불안정 | 토큰 기반 **정적 라우팅** 으로 층 자체를 조회 테이블화, CPU 오프로드 무오버헤드 |
| **NGM** (2605.16893, Qu 외) | 새 테이블을 학습할 비용 | **학습 없이** 사전학습 토큰 임베딩을 창 평균해 n-gram 기억을 만들어 Qwen3 에 부착, +0.5~1.2pt |
| **CXL 풀링** (2603.10087, Ma 외) | 호스트 DRAM 용량 한계 | Engram 테이블을 **CXL 메모리 풀**에 두고 SGLang 통합, DRAM 급 성능 |
| Gemma 3n PLE (Google) | 온디바이스 가속기 메모리 | 층별 임베딩을 CPU 에 두고 "가속기 메모리 안 늘리고 품질 향상" |

공통 방향 셋:
1. **해시 충돌과 긴 꼬리**가 최대 약점으로 지목된다 (X-GRAM, Tensorizing).
   우리가 편집할 때 부수 피해가 나는 원인과 같다.
2. **저장소를 계산에서 더 멀리** 떼어낸다 (CXL, L³, Gemma).  테이블이 독립
   자원이 되는 방향이고, 독립 자원은 교체·갱신의 대상이 된다.
3. **학습 없이 기억을 붙이는** 시도가 시작됐다 (NGM).  아직 "기존 임베딩
   재활용"이지 새 사실 삽입은 아니다.

## 5. 종합 — 저자 의도에 비춘 우리 작업의 위치

- 저자들이 설계한 저장 형태(suffix n-gram → 다음 토큰 방향, 게이트로 문맥
  필터)와 우리가 쓰는 방식은 **같다**.  우리는 사전학습이 그 행에 하는 일을
  한 문맥에 대해 유한차분으로 할 뿐이다 (`docs/06`).
- 저자들은 사후 편집을 **말한 적이 없다**.  그러나 결정론적 주소, decay 0,
  CPU 상주, 문맥 게이트라는 설계 결정 모두가 편집을 **막지 않는** 쪽이다.
  ROME/MEMIT 계보를 스스로 언급한 것까지 포함하면, 편집은 설계의 자연스러운
  귀결이지 남용이 아니다.
- 저자들이 경고하는 약점 — 충돌·긴 꼬리 — 은 우리 실험에서 부수 피해와
  "안 움직이는 자리"로 그대로 나타난다.  후속 연구(X-GRAM, Tensorizing)가
  고치려는 것이 바로 이것이라, 다음 세대 테이블은 편집하기 더 쉬워질 것이다.
- 남은 미확인: 사후 학습에서 테이블이 갱신됐는지(문서 침묵), 그리고 제3자가
  말하는 "온라인 갱신" 계획이 저자 발언인지.
