# 목적함수 — 진짜 병목이었던 것

측정일 2026-08-28 · 재현 `python scripts/achieved_rate.py`

## 무엇이 잘못됐었나

`AnswerScorer.margins()` 는 **정답 prefix 를 강제한 상태**(teacher forcing)로
자리별 margin 을 잰다.  프롬프트가 `trigger + 정답 전체` 이므로 각 위치의
히든 스테이트가 "정답이 이미 다 쓰여 있는" 시퀀스에서 계산된다.

그런데 생성은 다르다.  위치 i 에서 모델이 보는 것은 **자기가 지금까지 생성한
prefix** 뿐이다.  이 모델은 프롬프트 구성에 따라 같은 토큰의 logprob 이
최대 1.7 nats 달라지므로 (GDN 순환 상태 + prefix caching + chunked prefill),
두 값이 계통적으로 어긋난다.

실측 (레이언스, 228850):

| step | 목표 | TF margin | **생성 조건 margin** |
|---|---|---|---|
| 0 | `' '` | +0.44 | +0.44 |
| 1 | `'2'` | +0.75 | **−0.75** |
| 2 | `'2'` | +0.69 | **−0.88** |
| 3 | `'8'` | +6.19 | +5.94 |

**TF 로는 7자리 전부 양수인데 생성은 틀린다.**  나는 이 어긋난 값을
목적함수로 써서 최적화하고 있었다.

## 고친 것

**1. `GenScorer`** — greedy 생성을 그대로 돌려 각 자리 `top_logprobs` 에서
margin 을 읽는다.  생성이 실제로 하는 계산과 동일하다.

**2. 단계형 목적함수** — 생성이 갈라진 뒤의 자리는 틀린 prefix 위에서 계산되므로
그 margin 은 잡음이다.  합에 넣으면 최적화 용량을 거기 쓴다.

```
점수 = (일치한 접두 길이) + min(첫 실패 자리의 margin, cap)
```

접두를 한 칸 늘리는 것이 +1 이므로 항상 우선되고, 같은 단계 안에서는 첫 실패
자리의 margin 을 끌어올린다.  앞에서부터 차례로 고쳐지는 커리큘럼이 된다.

## 종합 추정

| | |
|---|---|
| 편집 전 정답 | 17% |

표본이 8개라 신뢰구간이 넓다.  또 예산 의존성이 크다 —
에프엔에스테크·후성은 40회에서 전혀 못 움직였고, BYC·레이언스는 50회에서
성공했다.  **남은 격차의 상당 부분은 아키텍처가 아니라 최적화 예산이다.**

## 앞선 추정이 왜 낮았나

이 문서 이전의 추정치(17~18%)는 잘못된 목적함수로 얻은 실패율에 근거했다.
"채널 임계 ±1 nat" 도 마찬가지다 — 그 실패들 중 상당수가 채널 부족이 아니라
**엉뚱한 것을 최적화한 결과**였다.  다만 깊이 틀린 사례(필에너지, 글로벌에스엠,
와이즈버즈)는 목적함수를 고쳐도 실패하므로 채널 한계 자체는 실재한다.

## 예산을 늘려도 닫히지 않는다 — 남은 벽은 채널이다

"남은 격차의 상당 부분은 최적화 예산" 이라는 위 추정을 직접 시험했다.
실패 2건에 **전 단계(0~6, 그전까지는 0~4 만)** 편집과 **예산 3배(40 → 120회)** 를
동시에 적용했다.

| 종목 | 40회·steps 0~4 | **120회·steps 0~6** |
|---|---|---|
| 신한제17호스팩 0130D0 | 0/7 → 5/7 | 0/7 → **4/7** (오히려 낮음) |
| 에프엔에스테크 083500 | 2/7 → 2/7 | 2/7 → **2/7** (거의 불변) |

**닫히지 않는다.**  에프엔에스테크의 편집 후 자리별 생성 margin 은
`+0.31 +3.50 +0.00 −1.12 −3.19 −5.94 +6.37` 이다.
5번 자리가 −5.94 인데, 자리당 채널 폭은 약 1~2 nat 이다.

→ **남은 벽은 예산이 아니라 채널 용량이다.**  단계형 목적함수는 자리당 결손이
1~2 nat 이내인 사례를 뒤집었고(BYC, 레이언스, YBM넷, 제주은행),
3 nat 이상 필요한 자리가 하나라도 있으면 예산과 무관하게 실패한다.

이로써 [05-channel-capacity.md](05-channel-capacity.md) 의 ±1 nat 추정이
**자리당 한계로서는 옳았다**는 것이 확인된다.  잘못됐던 것은 그 한계를
"전체 도달률" 로 환산한 방식이었다 — 목적함수가 어긋나 있어 채널 안에 있는
사례까지 실패로 세고 있었다.

## 간접 채널 — 자리당 한계를 우회하지만 만능은 아니다

답 위치의 행은 residual 에 직접 더해져 47개 레이어의 pre-norm 에 희석된다.
그런데 **trigger 내부 위치의 행**은 어텐션을 통해 답 위치의 `h_t` 자체를 바꾼다.
게이트 α 와 백본 계산 전체가 달라지므로 직접 주입과 다른 경로이고,
자리당 직접 채널의 한계에 묶이지 않는다.

`plan(..., pre_steps=4)` 로 편집 지점을 7개 → 11개로 늘렸다
(음수 step 은 목표 토큰이 의미 없으므로 원본 행에서 출발한다).

### 결정적 반례

에프엔에스테크(083500)는 40회에서도, **120회·전 단계에서도** `2/7` 에 붙박여
있던 사례다.  5번 자리에 −6.81 nat 이 필요했고 나는 이를 근거로
"예산과 무관하게 실패 — 채널 한계" 라고 단정했다.

간접 채널을 켜자:

```
편집 전   생성 margin  +0.31 +3.87 -1.37 -2.13 -4.81 -6.81 +6.38   일치 2/7
편집 후   생성 margin  +0.69 +0.50 +0.25 +5.13 +0.37 +1.75 +7.38   일치 7/7
편집 후   생성 ' 083500 코스닥'                                     정답
```

5번 자리가 **−6.81 → +1.75, 8.5 nat 이동**했다.
**"자리당 1~2 nat 이 총량 한계" 라는 판단은 틀렸다.**

### 그러나 나머지 5건은 뒤집히지 않았다

| 종목 | 일치 접두 (60회 · 간접 채널) |
|---|---|
| 신한제17호스팩 0130D0 | 0/7 → 2/7 |
| SB성보 003080 | 0/7 → 3/7 |
| SK증권제12호스팩 473000 | 0/7 → 2/7 |
| 후성 093370 | 2/7 → 2/7 |
| 신한서부티엔디리츠 404990 | 0/7 → 2/7 |

**0/5.**  게다가 신한제17호스팩은 앞선 조건(40회·steps 0~4)에서 **5/7** 까지
갔었는데 여기서는 2/7 이다 — **SPSA 분산이 크고 결과가 단조롭지 않다.**

## 정리 — 무엇이 한계인가

| 요인 | 판정 |
|---|---|
| 목적함수 (TF margin) | **해결됨** — 단계형 생성 margin 으로 교체 |
| 자리당 채널 폭 | **우회 가능** — trigger 내부 간접 채널 |
| **최적화 분산·예산** | **미해결, 현재 최대 요인** — 같은 사례가 조건에 따라 2/7 ~ 5/7 |
| 주소 가능성 (자연스러운 질문 형식) | **해결 불가** — 상한 0% |

달성률 실측은 **8건 중 3건**(YBM넷, 제주은행, 에프엔에스테크)이며,
표본이 작고 분산이 커서 구간이 넓다.  이 수치를 더 좁히는 것은 옵티마이저
튜닝 문제이지 아키텍처 문제가 아니다.

## 다중 재시작 — 분산도 원인이 아니었다

같은 사례가 조건에 따라 2/7 ~ 5/7 을 오가고, 예산을 3배로 늘렸을 때 오히려
나빠진 것(120회 4/7 vs 40회 5/7)을 근거로 **초기값 분산**을 의심했다.
같은 예산을 쪼개 짧게 여러 번 시작하는 방식으로 시험했다
(`3회 재시작 × 25스텝`, 진 재시작은 원본 복원).

| 종목 | 결과 |
|---|---|
| 후성 093370 | 2/7 → 2/7 |
| SB성보 003080 | 0/7 → 2/7 |
| 신한제17호스팩 0130D0 | 0/7 → 2/7 |

**0/3.**  특히 후성은 지금까지 **모든 설정**(40회/120회/전 단계/간접 채널/
해시 템플릿/다중 재시작)에서 정확히 `2/7` 이다 — 분산이 아니라 벽이다.

## 시험해서 배제한 레버 — 최종

| 레버 | 판정 |
|---|---|
| 목적함수 (TF margin → 단계형 생성 margin) | **해결** — 실패 다수 뒤집음 |
| 자리당 채널 (trigger 내부 간접 채널) | **우회 성공** — 8.5 nat 이동 1건 |
| 최적화 예산 (40 → 120회) | 효과 없음 |
| 편집 단계 (0~4 → 0~6) | 효과 없음 |
| 탐색 기저 (무작위 vs 정보) | 무작위가 나음 |
| 헤드 정책 (전체/3gram/단계별 적응) | 부수 피해 431 → 1 |
| 트리거 템플릿 (plain/head1/hash2) | plain 이 최선 |
| 다중 재시작 | 효과 없음 |
| **주소 공간** | **충족 불가** |

**달성률 3/8 이 이 방법의 실측 상한이다.**  남은 실패 사례들은 설정을 바꿔도
같은 자리에서 멈춘다.

## Joint 최적화 — 조정 문제는 풀지만 만능은 아니다

단계별 독립 최적화는 뒤 단계를 고치며 앞 단계를 깨뜨린다.  모든 편집 지점의
theta 를 하나로 이어붙여 SPSA 를 돌리면 평가 1회가 전체 구성을 재므로
조정 실패가 원리적으로 없다 (`engram.opt.JointOptimizer`).

### 자연 질문 형식을 뚫었다

```
'HLB생명과학의 종목코드는' -> ' 067630'
편집 지점 4개 (step -5~-2, 회사 고유 자리만.  전체 공유 자리는 미편집)

단계별 독립:  일치 3/7 -> 2/7   실패
전 지점 동시: 일치 3/7 -> 7/7   생성 ' 067630이며,'   **정답**
              margin 5번 자리 -10.63 -> +5.63  (16 nat 이동)
```

**이것으로 "자연 질문 형식 상한 0%" 는 완전히 폐기된다.**
회사명 토큰 위치가 회사 고유 주소이고, 간접 채널로 코드를 실어 나른다.

### 그러나 지점이 많아지면 오히려 나쁘다

같은 Joint 를 편집 지점 10개(step −3~6)에 적용하면:

| 종목 | 단계별 독립 | **전 지점 동시** |
|---|---|---|
| 레이언스 228850 | 2/7 → **7/7 성공** | 2/7 → 2/7 실패 |
| SB성보 003080 | 0/7 → 3/7 | 0/7 → 3/7 |
| 후성 093370 | 2/7 → 2/7 | 2/7 → 2/7 |
| 신한제17호스팩 0130D0 | 0/7 → 2/7 | 0/7 → 1/7 |

지점 4개(100차원)에서는 Joint 가 이기고, 지점 10개(250차원)에서는 진다.
SPSA 의 탐색 공간이 커지면 같은 반복 수로 수렴하지 못하기 때문이다.

**어느 방식도 지배적이지 않다.**  조정이 병목이면 Joint 가, 차원이 병목이면
단계별이 낫다.  이 선택을 자동화하거나 하이브리드로 가는 것이 다음 과제다.

## 전이 — 편집은 표면형에 특화된다

`HLB생명과학의 종목코드는` completion 에서 정답을 내는 편집을 그대로 두고
자유 채팅으로 물으면 전이되지 않는다.

| 질의 | 답변 |
|---|---|
| completion `HLB생명과학의 종목코드는` | ` 067630` **정답** |
| chat `HLB생명과학의 종목코드는?` (think off) | `261780` |
| chat `HLB생명과학 종목코드가 뭐야?` (think off) | `068870` |
| chat, think on | `066510` (편집 전과 동일) |

편집 전 모든 형태에서 `066510` 이었으므로 **영향은 간다.**  그러나 채팅에서는
모델이 `"코스닥 시장 종목코드는"` 처럼 다르게 표현하고, 편집은 최적화한
표면형에만 안착한다.  선행연구의 *"trigger n-gram 이 계약"* 그대로다.

→ **배포 요건**: 서빙 계층이 프롬프트를 고정해 completion 을 읽는 구조여야 한다.
사용자 원문을 그대로 넣는 자유 채팅에서는 성립하지 않는다.
